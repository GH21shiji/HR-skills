# 飞捷科思候选人岗位匹配

## 目标

基于候选人可验证经历与公司当前有效 JD，给出克制、可追溯的岗位匹配判断。区分技术方向匹配、职级匹配和录用风险，不因职位名称或关键词重合而高估。

## 必须读取的参考

- 每次评估先读 [references/matching-rubric.md](references/matching-rubric.md)。
- 做公司全岗位匹配、Top 3、岗位推荐或岗位盘点时，再读 [references/current-job-catalog.md](references/current-job-catalog.md)。
- 需要标准化回复或多人排序时，再读 [references/output-templates.md](references/output-templates.md)。

## 事实源优先级

1. 用户本轮提供的 JD 或领导口径。
2. 飞书招聘系统当前“开放中”的职位详情。
3. `current-job-catalog.md` 的缓存画像。
4. 通用行业常识。

若用户说“最新岗位”“所有在招岗位”或缓存日期可能过期，使用 `web-access` 只读刷新飞书岗位列表；不得修改职位或候选人状态。若只拿到职位名称而未读到详情，明确将判断标为“基于岗位画像的初步匹配”。

## 工作流

### 1. 完整读取候选人材料

- PDF：调用 PDF skill，提取全部页面并进行渲染检查。
- 截图：读取截图中所有可见信息；缺页时明确“基于当前截图”。
- 网页：按对应网页 skill 读取，不自行跨越登录或权限边界。
- 记录教育、工作年限、近期岗位、项目角色、技术栈、量化结果、论文/专利、地点、薪资和到岗时间。

### 2. 建立候选人能力画像

将经历拆成以下维度，不直接沿用候选人自述标签：

- 物理与数值算法；
- C++与软件工程；
- GPU/CUDA/HPC；
- 仿真引擎与求解器；
- 可微分编程；
- 大模型、VLA与强化学习；
- 云平台、数据与分布式系统；
- 机器人本体、ROS与嵌入式；
- 产品、项目、交付和商业化；
- 职级、团队范围与工程责任。

### 3. 先判方向，再判职级

分别回答：

1. 候选人的核心技术方向是什么；
2. 能承担哪个模块；
3. 是否达到目标岗位职级；
4. 是成熟即战力、可培养人才，还是仅邻近方向。

架构师、负责人、Leader 不得仅凭博士学历、论文或项目负责人称谓判定。

### 4. 进行岗位评分

按 `matching-rubric.md` 的证据等级、权重和封顶规则评分。输出最匹配的 1～3 个当前岗位；若没有合适岗位，直接说明“当前无匹配岗位”，不得强行推荐。

匹配度是区间估计，默认使用 5～10 个百分点的区间，不使用虚假精确分数。

### 5. 给出初筛动作

只能使用以下结论：

- 建议优先约面；
- 建议通过初筛；
- 建议人工复核/先补充材料；
- 建议调整岗位后推进；
- 当前岗位不通过。

说明下一步需要验证的 3～6 个问题。未经用户确认，不发送消息、不推进约面、不修改系统状态。

## 比较与排名

- 比较候选人时使用同一岗位、同一权重和同一证据标准。
- 将“技术方向匹配”和“职级成熟度”分列，避免科研新人因理论强被误评为架构师。
- 各岗位 Top 3 可以重复出现同一候选人，但要说明其第一选择岗位。
- 证据不足时宁可降低置信度，不用主观印象补齐。

## 输出原则

- 先给结论和是否推进，再给原因。
- 区分“本人实现”“主导设计”“参与项目”“管理项目”和“熟悉概念”。
- 明确最匹配岗位、备选岗位、不匹配岗位以及原因。
- 对薪资、稳定性、任职时间重叠、学历和到岗时间单独提示，不混入技术匹配分数。
- 不输出候选人的电话、邮箱等无关个人敏感信息。
