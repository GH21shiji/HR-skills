# Offer 记录自动填充

将审批页作为事实来源，将数据写入用户指定的多维表格记录。不要把审批通过解释为候选人接受 Offer。

## 默认资源

使用前由用户提供目标 Base URL，或配置自己的以下标识：

- Base：`https://<tenant>.feishu.cn/base/<base_token>?table=<table_id>&view=<view_id>`
- Base token：`<base_token>`
- Table ID：`<table_id>`
- View ID：`<view_id>`

## 必用能力

使用并遵守当前环境中的 `lark-base`、`lark-approval`、`lark-contact`、`web-access` 和 `computer-use` 技能。先完整读取各自的 `SKILL.md`；认证或权限问题按 `lark-shared` 处理。

## 工作流程

1. 确认目标行号或记录范围。单行请求直接处理；批量请求先说明预计处理范围。
2. 用 `lark-cli base +field-list` 读取真实字段结构，不凭记忆写字段。
3. 按用户给出的视图读取目标记录。行号按视图中的数据行计算：`offset = 行号 - 1`，`limit = 1`。保存返回的 `record_id`。
4. 读取 `offer审批链接`。链接为空时停止该行并报告；不要覆盖其他字段。
5. 若链接为 `go.feishu.cn/approval/s/...`，先用公开跳转解析出内部 `InstanceID`。开放审批接口通常不能直接读取该数字 ID，不要在 `instances get` 上重复尝试。
6. 在新的后台浏览器标签页打开审批链接，使其进入已登录的飞书客户端；不要操作或关闭用户原有标签页。
7. 用 Computer Use 读取飞书客户端审批详情。以详情区为准，不要把左侧审批列表中的其他候选人混入当前记录。读取完关闭自己创建的浏览器标签页。
8. 提取并映射字段，遵守下表。
9. 写入前再次确认目标 `record_id`。用户明确要求录入或回填即视为已授权该次普通记录更新。
10. 用 `lark-cli base +record-upsert --record-id ...` 更新记录，再用 `+record-get` 复核每个写入字段。

## 字段映射

| 多维表字段 | 审批来源 | 规则 |
|---|---|---|
| `候选人姓名` | 候选人信息 → 姓名 | 原样写入 |
| `岗位` | Offer 信息 → 职位 | 先用 `+field-search-options` 查现有选项；只写完全匹配或语义唯一的现有选项 |
| `薪资-现金（月base）` | Offer 信息 → 月基本薪资 | 去掉币种和千分位，写数字 |
| `添加时间` | 审批头部 → 提交于 | 写绝对时间 `YYYY-MM-DD HH:mm:ss`；补全年份时以审批时间和当前日期判断，存在歧义则询问 |
| `负责HR` | 审批提交人 | 用 `lark-contact +search-user` 解析唯一 `open_id`，人员字段写 `[{"id":"ou_xxx"}]` |
| `候选人面试链接` | 面试评价中的面试记录链接 | 写完整 URL，保留所有参数 |
| `薪资-股权/年` | 明确的年度股权字段 | 没有明确股权数据就不写；年绩效奖金不是股权 |
| `薪资-签字费` | 明确的签字费字段 | 没有明确数据就不写，不把缺失值改为 0 |
| `候选人状态` | 候选人接受、拒绝或入职的明确事实 | 审批通过不等于接受 Offer；没有明确事实就留空 |

## 保守规则

- 不覆盖已有非空值，除非用户明确要求更新或审批内容能证明旧值错误。
- 岗位没有完全匹配时，只在唯一候选项明显等价时采用，并在结果中说明映射；存在两个以上合理选项时先询问。
- HR 搜索命中多人时不擅自选择。
- 不写只读字段，不用普通记录接口写附件。
- 单行失败不影响其他行；批量处理时逐行记录成功、跳过和失败原因。
- 最终报告写入字段、保留字段、任何岗位映射和复核结果。

## 常用调用
